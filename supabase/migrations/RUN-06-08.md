# How to run migrations 06, 07 and 08

These three files get the database ready for activities. Plan on about ten minutes.

## Read this first

- **Order matters: 06, then 07, then 08.** Finish the check for one before starting the next.
- **The live site keeps working after each one.** The family page and the admin page do not use anything new yet.
- **Nothing visible changes.** You will not see activities anywhere until the new pages ship. That is expected.
- **No data is added, changed or removed.** These files only add structure: empty tables, rules and functions. Your schedule, switches, notes and the family link are untouched.
- **Each file is safe to run twice.** If you are not sure whether one ran, run it again.
- **Pick a quiet moment.** While file 06 runs, the admin page waits for a second or so if someone is using it at that instant. Nothing is lost, it just pauses. The family page is not affected.
- **Save a copy first** (the next section). It takes two minutes and means there is always a way back.
- These files were tested in a throwaway test database on a laptop, including running each one twice. They have **not been run in your Supabase project yet**. The checks below are how you confirm each one worked there.

If the files are applied for you through the Supabase connector instead of being pasted by hand, skip the "Run it" parts and go straight to each "Check it" part.

## Before you start: save a copy of your schedule

These files do not change your schedule data. Save a copy anyway, so you never have to take that on trust.

1. Make a folder **outside** the `Kids_Tracker` folder, for example `Documents/Kids Tracker backups/` with today's date in the name. It must not be inside the repo, because the repo is public.
2. In Supabase, open the project **Kids' Tracker** and click **Table Editor** in the left sidebar.
3. Click the table **settings**. Use the **Export** button above the grid and choose **Export table as CSV**. Save the file into your backup folder.
4. Do the same for **breaks**, **swaps** and **swap_details**.

You should end up with four files. Keep them until the new pages have shipped and you are happy.

## Where to go

1. Open https://supabase.com/dashboard and choose the project **Kids' Tracker**.
2. In the left sidebar, click **SQL Editor**.
3. Click **New query** (the plus button near the top of the editor's list). You get an empty box.

You will repeat step 3 for each file and for each check, so every paste starts in an empty box.

## Step 1: file 06 (new tables and the second sign-in role)

### Run it

1. Open `supabase/migrations/06_activities_tables.sql`, select everything and copy it.
2. Paste it into the empty query box.
3. Click **Run** (or press Cmd + Enter).

Supabase may show a warning that the query has a "destructive operation". That is expected. The file contains `drop policy if exists` and `drop trigger if exists` lines for rules on the brand-new tables, and it swaps one rule on the sign-in list (the rule that says which roles are allowed) for a new one. No table, column or row is dropped. Confirm and run.

**What you should see:** `Success. No rows returned`.

### Check it

New query, paste this, Run:

```sql
select
  (select count(*) from pg_tables where schemaname = 'public') as tables,
  (select count(*) from pg_tables where schemaname = 'public' and rowsecurity) as tables_with_security_on,
  (select count(*) from pg_policies where schemaname = 'public') as rules,
  (select count(*) from pg_trigger g
     join pg_class c on c.oid = g.tgrelid
     join pg_namespace n on n.oid = c.relnamespace
    where n.nspname = 'public' and not g.tgisinternal) as triggers;
```

**Expected:** one row.

| tables | tables_with_security_on | rules | triggers |
|---|---|---|---|
| 14 | 14 | 22 | 26 |

The first two numbers must match each other. That is the proof that every table has row level security on.

Second check. New query, paste, Run:

```sql
select pg_get_constraintdef(oid) as role_rule
from pg_constraint
where conrelid = 'public.app_users'::regclass and contype = 'c';
```

**Expected:** exactly one row that reads `CHECK ((role = ANY (ARRAY['admin'::text, 'parent'::text])))`.

Optional third check, counts only:

```sql
select role, count(*) from public.app_users group by role;
```

**Expected:** only `admin`, with the same count you had before. There is no `parent` row yet. This file does not add the other parent's sign-in. That is a separate, later step.

Then open the admin page and the family page as usual. Both should look and work exactly as before.

## Step 2: file 07 (the schedule for a signed-in parent)

### Run it

1. New query.
2. Copy all of `supabase/migrations/07_editor_schedule.sql`, paste, **Run**.

**What you should see:** `Success. No rows returned`.

### Check it

New query, paste, Run:

```sql
select
  public.get_schedule('not-a-real-link') is null as bad_link_gets_nothing,
  public.get_editor_schedule() is null           as not_signed_in_gets_nothing;
```

**Expected:** one row, both `true`.

Second check. This lists the names of the sections the real family link returns. It shows names only, never your schedule and never the link itself:

```sql
select k.field
from jsonb_object_keys(
       public.get_schedule((select token from public.share_links where active limit 1))
     ) as k(field)
order by k.field;
```

**Expected:** four rows: `breaks`, `changed_at`, `settings`, `swaps`. The same four as before this file. (If the family link is turned off, this returns no rows. That is fine.)

Then open the family page on your phone and pull to refresh. It should look exactly as it did.

## Step 3: file 08 (activities go to the family link)

### Run it

1. New query.
2. Copy all of `supabase/migrations/08_get_schedule_activities.sql`, paste, **Run**.

**What you should see:** `Success. No rows returned`.

### Check it

New query, paste, Run (the same query as in Step 2):

```sql
select k.field
from jsonb_object_keys(
       public.get_schedule((select token from public.share_links where active limit 1))
     ) as k(field)
order by k.field;
```

**Expected:** eleven rows: `breaks`, `changed_at`, `comments`, `events`, `kids`, `log`, `places`, `settings`, `swaps`, `teams`, `window`. The original four are still there. Of the seven new ones, six (`comments`, `events`, `kids`, `log`, `places`, `teams`) are empty lists for now because no activities have been entered, and `window` is a small item holding two dates: the first and last day of activities the family link would show.

Second check. This confirms the family link carries no private field. It returns a single true or false:

```sql
select public.get_schedule((select token from public.share_links where active limit 1))::text
       ~ '"(pnote|track_from|ical_url|phone|lat|lng|before|after|source_uid)":' as private_fields_found;
```

**Expected:** `false`. (Empty if the family link is turned off.)

Then open the family page and the admin page once more. Both should look exactly as before.

### Final security check

New query. Copy all of `supabase/migrations/CHECK-06-08.sql`, paste, **Run**.

**Expected:** a table of about 145 lines. Every line says `OK`, `KNOWN` or `INFO` in the status column. Click the **status** column header to sort, or scroll: there should be no line that says `PROBLEM`. If there is one, copy that line and send it over before doing anything else.

`KNOWN` lines are about `rls_auto_enable`, a function Supabase added when the project was created. It is left alone on purpose.

### Check from the outside (optional, two minutes)

Everything above was checked from inside Supabase. This last check knocks on the door the way a stranger on the internet would: with only the public key from `config.js` and no sign-in. Every knock should be refused.

1. Open the **Terminal** app on your Mac.
2. Open `config.js` and find the Supabase address (it starts with `https://` and ends with `.supabase.co`) and the public key.
3. Paste these two lines into Terminal, one at a time, with your values between the quotes. Press Return after each.

```sh
URL="paste the Supabase address here"
KEY="paste the public key here"
```

4. Paste this whole block and press Return:

```sh
for f in my_role is_editor my_who kt_schedule_core get_editor_schedule; do
  printf "function %s: " "$f"
  curl -s -o /dev/null -w "%{http_code}\n" -X POST "$URL/rest/v1/rpc/$f" \
    -H "apikey: $KEY" -H "Content-Type: application/json" -d '{}'
done
for t in settings breaks swaps swap_details share_links app_users kids events event_log contacts homes; do
  printf "table %s: " "$t"
  curl -s -o /dev/null -w "%{http_code}\n" "$URL/rest/v1/$t?select=*&limit=1" -H "apikey: $KEY"
done
printf "family link with a made-up code: "
curl -s -X POST "$URL/rest/v1/rpc/get_schedule" \
  -H "apikey: $KEY" -H "Content-Type: application/json" -d '{"p_token":"not-a-real-link"}'
echo
```

**Expected:** sixteen lines that each end in `401` (a `403` also means refused), then a last line that ends in `null`. The block only prints those numbers. It never prints anything from a table.

If any line ends in `200`, that door is open and should not be. Send the line over before doing anything else. (Before file 06 was run, `my_role` answered `200`. After it, `401`. That change is one of the things this migration is for.)

This check was written from how Supabase's API is documented to answer. It has not been tried against your project, so treat an unexpected number as a question to ask, not as an emergency.

## If something goes wrong

- **You see a red error instead of "Success".** Copy the whole error message and note which file you were running. Supabase runs each paste as one unit, so a file that stops with an error should leave the database as it was before that paste. Either way, every file is safe to run again once the cause is fixed.
- **Something looks wrong with your schedule afterwards.** It should not, because these files do not write to it. If it ever did, the four files you saved at the start are the way back. Do not try to load them yourself. Send a note and keep the files where they are.
- **You are not sure which step you are on.** Run the first check from Step 1. If `tables` says 6, file 06 has not run. If it says 14, it has. Then run the first check from Step 2. An error that says `get_editor_schedule` does not exist means 07 has not run. Then run the second check from Step 2. Four rows means 08 has not run. Eleven rows means all three are done.
- **You ran a file twice, or out of order.** Twice is harmless. Out of order: 07 and 08 stop with an error if 06 is missing, and 08 stops if 07 is missing. Just run them again in order.
- **A check shows a different number.** Do not rerun anything. Send the result as is. A different count usually means the live database had something this file did not know about, and that is worth a look before moving on.
- **The family page or admin page looks different or shows an error.** This should not happen. Tell the developer which step you had just finished. Rerunning the same file will not hurt.

## What these files do not do

- They do not create the other parent's sign-in. That comes later, as its own step, and never goes in this repo because it involves an email address.
- They do not enter kids, places, teams, addresses or phone numbers. Those are typed into the new Activities page once it ships.
- They do not change what the live pages show.
